## 1. 何を作るのか・なぜ作るのか

Cay 先生の講義「自然言語の指示を、安全が保証されたロボットの行動に変える」の考え方を、Unitree Go2 で動く形にする。

- **講義の結論：** LLM に任せるのは「言葉 → 形式仕様（LTL）」の翻訳だけ。正しさと安全は、オートマトンと監督制御という保証付きの計算で守る。
- **先に用意しておくもの：** 「Go2 の状態遷移図（環境）」と「ロジックの単語帳・文法」の2つ。
- **ねらい（ユーザーの言葉）：** 先に用意した2つの範囲内なら「任意の指示」ができる。指示が変わってもプログラムは書き換えない。式が変わるだけで、組み合わせ（sync → trim → 監督器 → 計画）は自動で計算される。
- **今回はシミュレーション：** この Mac（Apple Silicon）からは、有線で Go2 の実機を動かせないことがわかった（Mac の Docker は DDS が LAN に届かない。Unitree 公式も Mac は非対応）。そこでシミュレーションの Go2 で作る。
- **最終的な使い方（ユーザーの理想）：** プログラムを全部ここで書いておき、Go2 と有線でつないだ Linux PC にフォルダごと移す。そうすれば実機がそのまま動く。

## 2. ゴール

1. **押している間だけ話す：** ブラウザのページを開いた状態で、スペースキーを押している間だけマイクがオンになる。離したら、そこまでを1つの指示として扱う。
2. **書き起こし：** 日本語の音声を文字にする。
3. **翻訳：** LLM が、文字にした指示を LTLf の式に翻訳する。LLM は Claude（Claude Code CLI、`claude -p`）と Codex（Codex CLI、`codex exec`）を設定1つで切り替えられる（§5）。
   - プロンプトは講義の4パート（Grammar / Vocabulary / Examples / Query）で作る。
   - 出力は構造化出力（`{"formula": "..."}`）で受ける。
   - `check()` で検証し、不合格なら却下理由を添えて聞き直す（最大3回）。
4. **ここから下は LLM を使わない：** 式 → formula progression（講義 5.2）で要求オートマトン（SPEC）を作り、SAFE と合わせて meet → 環境オートマトンと meet → trim → supcon（監督器）→ 計画（最短経路）→ 実行。
5. **状態遷移図を画像にして見せる：** 指示のたびに作った状態遷移図をページに表示する。対象は、要求（SPEC）、環境（PLANT）、積（PRODUCT）または trim 後（TRIMMED）、監督器（SUP）。計画の道筋と今いる状態は色で示す。
6. **シミュレーションの Go2 が動く：** 実機と同じ ROS 2 の窓口で指令を受け、状態を返す。シミュレーションは2種類用意し、起動のしかたで切り替える。
   - **にせ Go2（§9）：** 自動テスト用。速く、結果が毎回同じ。
   - **Gazebo の Go2（§9.1、ユーザーの指定）：** 立つ・伏せる・歩く・旋回が、物理シミュレーションの中で実際に動くことを目で確かめる用。
7. **止める・切り替える：**
   - 「止まって」「ストップ」「停止」は、Claude を通さず、すぐ StopMove を送る。
   - 動いている途中に新しい指示が来たら、いったん止めてから新しい計画に切り替える。
8. **センサーで、ぶつかりそうになったら止まる（ユーザーの希望）：**
   - LiDAR の点群（`/utlidar/cloud`）から、前方・後方に近い物があるかを毎周期（10 Hz）判定する。
   - 動いている途中に近い物が現れたら、すぐ StopMove を送って止まる。
   - 監督器は、その向きへの移動を禁止する（不可制御イベント）。物がなくなれば、続きから動く。
   - センサーが途切れたときも移動を止める。
   - シミュレーションでは、ページのボタンで Go2 の前や後ろに箱を置ける。歩いて近づくと、実際に点群で検知して止まることを確かめる。
9. **Linux PC に移せる：** フォルダを Go2 と有線でつないだ Linux PC に移し、ごく少ない変更で実機を動かせる。

## 3. やらないこと

- MuJoCo や Isaac Sim。物理シミュレーションは Gazebo だけを使う（§9.1）。
- 座る・挨拶・ダンスなどの、Gazebo での物理的な再現。これらは Go2 本体の中のソフトにしかない動きなので、Gazebo では「ふり」にする（§9.1）。
- 場所の名前（台所、ソファなど）と、地図を使ったナビゲーション。単語帳は Go2 のプリセットの動作と姿勢だけで作る（ユーザーの希望から決めた。§7）。
- 低レベル制御（`/lowcmd`）と強化学習。
- Mac の Docker から実機の Go2 へつなぐこと。
- 返事の読み上げ（音声合成）。
- 常時聞き取り。マイクはスペースを押している間だけオンにする。

## 4. 失敗とみなすこと（動いても、これなら失敗）

- 翻訳以外を LLM が決める。たとえば LLM が行動の列を直接出し、それがそのまま実行される。講義の結論に反する。
- `check()` と DFA と監督器を通らずに、Go2 へ指令が出る道がある。
- LLM の出力を黙って直す（括弧を補う、命題名を言い換えるなど）。講義の「Never repairs a formula」に反する。誤った式は不合格にして、聞き直す。
- シミュレーション専用の作りになり、Linux PC と実機では動かない。たとえば ROS 2 のトピックや型が実機と違ってしまう。
- 危ない動作（宙返り・逆立ち・二足歩行・ジャンプ）が語彙に入る。

## 5. 制約

### 動かす場所
- **開発機：** Apple Silicon の Mac（arm64）。Docker Desktop（engine 29.8.2、CPU 8、メモリ 8GB 割り当て）。
- **コンテナ：** Ubuntu 22.04 + ROS 2 Humble（公式 `ros:humble` 系イメージ）。Unitree 公式が推奨する実機用 PC と同じ構成にするため。
  - arm64 と x86_64 の両方でビルドできること（Linux PC が x86_64 の可能性が高い）。
- **全部コンテナの中で動かす：** 書き起こし、Claude 呼び出し、オートマトン計算、ROS 2、シミュレーションの Go2、Web ページのサーバー。Mac 側はブラウザを開くだけ。
  - Mac の Docker はマイクを直接使えない。そのためブラウザが録音して、音声をコンテナへ送る。
  - `http://localhost` はブラウザのマイク許可が使える安全な扱いなので、そこで開く。ページは `http://localhost:8810`（ポートは `GO2_UI_PORT` で変えられる。空なら既定の 8810）。
- **unitree_ros2：** コンテナ内でビルドする（`unitree_api`、`unitree_go` のメッセージ）。`source ~/unitree_ros2/setup.sh` がそのまま使えること。

### Go2 とのやり取り（実機と同じにする）
- `/api/sport/request` へ `unitree_api/msg/Request` を送る。`header.identity.api_id` で動作を選び、`parameter` に JSON を入れる。
- `/sportmodestate` から `unitree_go/msg/SportModeState` を受ける。`position`、`imu_state.rpy`、`error_code` を使う。
- `/utlidar/cloud` から `sensor_msgs/PointCloud2` を受ける（前方の障害物の判定）。
- `api_id` の値と姿勢の移り方は、zip の `go2_nl_control/actions.py` のものを使う（公式 `sport_api.py` と同じ番号）。

### LLM の呼び出し（Claude と Codex を切り替え）

ユーザーの指定：CLI を使う（API キーは使わない）。実際には Codex を使うかもしれない、とのこと。

- **どちらでも同じ部分：**
  - LLM の呼び出し部分を1つの窓口にまとめ、`env.txt` の設定1つ（例：`LLM_BACKEND=claude` / `codex`）で切り替える。
  - プロンプト（講義の4パート）、出力の形（§7.4.1 の JSON Schema）、`check()`、聞き直しの流れは同じにする。
  - コンテナの中にどちらの CLI も入れる。
- **道具は使わせない：** どちらの LLM にも、ファイル操作などの道具を使わせない。翻訳だけをさせる。トークンのファイルにも届かないようにする（最後の見直しの SEC-3、Ruling R37）。
  - Claude は `--tools ""`。Codex は `--sandbox read-only` に加えて、`--disable shell_tool --disable unified_exec --disable view_image`（シェルと画像の読み込みを外す）、`-c web_search="disabled"`、`--ignore-user-config`（`config.toml` の MCP サーバーなどを読まない）。codex-cli 0.166.0 の `codex features list` と `codex debug prompt-input` で確かめた。
  - CLI は、空の一時フォルダ（`/work` の外）を作業場所にして起動する。Codex は `-C` も同じフォルダにし、schema と答えのファイルはその外に置く。
  - 子のプロセスに渡す環境変数から、もう一方の LLM の秘密を除く。Codex には `CLAUDE_CODE_OAUTH_TOKEN`・`ANTHROPIC_*` を、Claude には `OPENAI_*`・`CODEX_*` を渡さない。
  - compose は、コンテナの中の `/work/env.txt` を `/dev/null` で覆う（`- /dev/null:/work/env.txt:ro`）。`env.txt` は、compose がホストで `env_file` として読むだけにする。
- **トークンの扱い：**
  - トークンや認証のファイルは `env.txt` か Docker のボリュームに置き、git や他人に渡さない。
  - 作る側は最初に、`go2/.gitignore` に `env.txt` と `.env` を入れる。
  - 私（作る側）はトークンの値を見ない・書かない・扱わない。
- **テスト：** どちらの CLI も呼ばずに試せるように、決まった返答を返す偽物の窓口を用意する。

**Claude（Claude Code CLI）**
- `claude -p` で呼ぶ。
- 確認済みのオプション（v2.1.303）：`--json-schema`、`--system-prompt`、`--tools`、`--model`、`--no-session-persistence`、`--output-format`。
- **`--bare` は使わない：** `--bare` だと認証が `ANTHROPIC_API_KEY` などに限られ、`setup-token` のトークンが使えないため（`claude --help` で確認）。
- **認証：**
  - ユーザーが Mac で `claude setup-token` を実行して長期トークンを作り、自分で `env.txt` に書く。
  - コンテナにはそれを環境変数として渡す。変数名は公式ドキュメントで確認すること。

**Codex（Codex CLI）**
- `codex exec` で呼ぶ。この Mac には今は入っていない。
- 公式ドキュメント（learn.chatgpt.com の Non-interactive mode）で確認したオプション：
  - `--output-schema <file>`：JSON Schema で出力の形を固定する
  - `-o` / `--output-last-message <path>`：最後の返答をファイルに書く
  - `--json`：イベントを JSON Lines で出す
  - `--skip-git-repo-check`：git リポジトリの外で動かす
  - `--ephemeral`：セッションを保存しない
  - サンドボックスは既定で読み取り専用
- モデルを選ぶオプションは、そのページには書かれていなかった。作る側が `codex exec --help` で確認する。
- **認証：**
  - ふつうは `codex login` で保存したログイン（`~/.codex/auth.json`）を使う。
  - コンテナの中で一度ログインし、`~/.codex` を Docker のボリュームに残す方法を README に書く。具体的なやり方は作る側が公式ドキュメントで確認する。
  - コンテナにはブラウザが無く、`docker compose run` はポートを出さないので、ふつうの `codex login`（localhost に戻ってくる）は終わらない。`codex login --device-auth`（端末に出るコードを、Mac のブラウザで入れる）にする（`codex login --help` で確認）。
  - API キーを使う場合は `CODEX_API_KEY` を使う。

### 安全（実機に移したとき）
- zip の `nl_control.py` にある仕組みを残す。
  - 終了時（q、Ctrl+C、kill、切断）に StopMove を3回送る。
  - 二重起動を防ぐ。
  - `/api/sport/request` に自分以外の送り手がいたら、起動を断る。そのときは StopMove を送らない（そのプログラムが動かしている Go2 に割り込まないため）。
  - センサーが 0.5 秒途切れたら移動を保留する。
  - 15 秒保留が続いたら計画を中止する。
  - 移動のタイムアウトがある。
- 動作の前に、README の注意（前方 1 m と周りを空ける、リモコンで止められる人がそばにいる）を出す。

### 使えることを確認した部品（PyPI）
- `pitct` 1.0.8：TCT の Python 版。Linux の aarch64 と x86_64、macOS arm64 のビルド済みファイルがある。graphviz に依存する。
- `flloat` 0.3.0：Python だけで書かれている。SPEC は formula progression（講義 5.2）で作る。flloat は式の読み取りとテストの照合に使う。

## 7. 世界のモデル（先に用意しておく状態遷移図と単語帳）

ここが「先に用意しておくもの」の本体。**1か所（設定のファイル1つ）にまとめ、1行足せば語彙が増える形にする。**

### 7.1 環境オートマトン（PLANT）

物の命題（near_〈id〉・around_〈id〉・around_cw_〈id〉）を使う指示は docs/superpowers/specs/2026-11-05-go2-objects-design.md に従う（物を使わない指示は、この節のまま）。

- **状態：** 姿勢 {伏せ LYING, 立ち STANDING, おすわり SITTING} × 前方 {なし, 近い物あり} × 後方 {なし, 近い物あり}。全部で 3 × 2 × 2 = 12 状態。
  - 初期状態は、Go2 が `/sportmodestate` で教える今の姿勢と、そのときのセンサーの判定。
  - ただし姿勢が立ち以外（伏せ・おすわり・不明）のときは、前方・後方とも「なし」として扱う。動けるのは立ちのときだけで、伏せていると LiDAR が地面や自分の脚を見て「あり」になるため。立ち上がった後に本当に物があれば、そこで `front_blocked`（`back_blocked`）が起きて、移動は待つ。
- **可制御イベント（Go2 のプリセット）：** 移り方は `actions.py` に従う。

| イベント | できる状態 | 移った先 |
|---|---|---|
| `stand`（StandUp → BalanceStand） | 伏せ | 立ち |
| `lie_down` | 立ち | 伏せ |
| `sit` | 立ち | おすわり |
| `rise_sit` | おすわり | 立ち |
| `hello`、`stretch`、`content`、`heart`、`scrape`、`dance` | 立ち | 立ち |
| `forward`、`backward` | 立ち | 立ち（距離は固定。既定 0.5 m） |
| `turn_left`、`turn_right` | 立ち | 立ち（角度は固定。既定 90 度） |

- **不可制御イベント（センサーが決める）：** どの姿勢でも、いつでも起こりうる。
  - `front_blocked`（前方：なし → あり）、`front_clear`（あり → なし）
  - `back_blocked`（後方：なし → あり）、`back_clear`（あり → なし）
- **いつも守る安全の決まり（指示とは別に、必ず足す）：** 指示の式には足さず、`World.forbidden`（ずっと禁止する可制御イベントの集合）として持つ。合成のときに、1状態の SAFE オートマトン（`forbidden` 以外の全イベントの自己ループ）にして要求オートマトンと合わせ、監督器（supcon）にかける（§7.5）。
  - 前方に近い物があるときは前進しない。式で書けば `G(obstacle_front -> !moved_forward)` にあたる。ラベルに `obstacle_front` と `moved_forward` の両方を含む前進イベントを `forbidden` に入れる。
  - 後方に近い物があるときは後退しない。`G(obstacle_back -> !moved_backward)` にあたる。ラベルに `obstacle_back` と `moved_backward` の両方を含む後退イベントを `forbidden` に入れる。
  - この2つは、式 `SAFETY_FORMULA`（`voice_ltl/world.py`）と同じ意味になる（禁止するイベントのラベルには両方の命題が入るため）。式は意味の説明とテストの正解に使い、合成の式には付けない。
  - 旋回は、その場で回るので止めない。ただし前方・後方の判定は旋回中も続ける。
- **動作の途中で止まる：** 前進・後退の途中で近い物が現れたら、実行器は動作の終わりを待たずに StopMove を送って止まる。
  - その動作は「保留」になり、物がなくなれば残りの距離を続ける。この保留と再開は zip の `executor.py` / `supervisor.runtime_permits()` の仕組みを使う。
  - オートマトンの上では「1回分の前進」を、途中で止まっても1つのイベントとして数える。完了したときに `moved_forward` が真になる。
- **判定の距離：** zip の `perception.py` と同じく、止まる距離と動き出す距離を分ける。0.5 m より近いと「あり」、0.7 m より遠いと「なし」に戻る。値がばたつかないようにするため。
- **後方の判定についての注意：** 実機の Go2 の LiDAR は頭の下についているので、真後ろは胴体の陰になって見えにくい可能性がある。
  - 実機に移したら、`python3 -m voice_ltl.sensor_check` で後方の物が見えるか確かめる（README §6 の手順 8）。この道具はアプリと同じ判定と一番近い距離を 0.5 秒ごとに出し、Go2 には何も送らない。前方も同じく確かめる（LiDAR の取り付けの値 `lidar_x`・`lidar_z`・`lidar_pitch` は仮の値のため）。rviz2 はイメージに入っていないので、使うなら Linux PC に入れる。
  - 見えない場合は、後退を語彙から外すか、ごく短い距離に限る。この判断は README に手順として書く。

### 7.2 単語帳（命題）

物の命題（near_〈id〉・around_〈id〉・around_cw_〈id〉）を使う指示は docs/superpowers/specs/2026-11-05-go2-objects-design.md に従う（物を使わない指示は、この節のまま）。

各ステップで真になる命題は、「移った先の状態」と「そのステップで行った動作」から決める（講義のラベリング写像 `label()` にあたる）。

- **姿勢：** `standing`、`sitting`、`lying`
- **動作をした：** `hello`、`stretched`、`content`、`heart`、`scraped`、`danced`、`moved_forward`、`moved_backward`、`turned_left`、`turned_right`
- **センサー：** `obstacle_front`、`obstacle_back`。指示の中でも使える。たとえば「前に何かあったら挨拶して」→ `G(obstacle_front -> F hello)`。

### 7.3 文法

講義の `!`、`&`、`F`、`G` に、`|`、`->`、`U`、`X`、括弧を足す。順番や「〜するまで〜しない」を言えるようにするため。講義ノートの補足にあるとおり、プロンプトの Grammar と `check()` の両方を直す（今の `check()` は F・G 以外の大文字を弾くため）。「最後は〜して」の書き方（flloat の `last` など）を入れるかは、作る側の判断（§11）。

### 7.4 指示の例と、期待する結果（受け入れテストに使う）

物の命題（near_〈id〉・around_〈id〉・around_cw_〈id〉）を使う指示は docs/superpowers/specs/2026-11-05-go2-objects-design.md に従う（物を使わない指示は、この節のまま）。

| 話す言葉 | 期待する式（例） | 期待する結果 |
|---|---|---|
| 立って挨拶して | `F hello` | 伏せからなら、stand → hello |
| 挨拶してからダンスして | `F(hello & F danced)` | stand → hello → dance |
| 挨拶するまで座らないで、そのあと座って | `(!sitting U hello) & F sitting` | stand → hello → sit |
| ダンスはしないで、伸びをして | `G !danced & F stretched` | stand → stretch |
| 前に進んで | `F moved_forward` | stand → forward。前方 0.5 m 以内に箱があれば、前進せずに待つ（不可制御イベント）。箱がなくなれば進む |
| 2メートル進んで（前方 1.2 m に箱を置いておく） | `F(moved_forward & X F(...))`（前進4回） | 歩いて箱に 0.5 m まで近づいた時点で、動作の途中でも止まる。箱をどけると続きを歩く |
| 後ろに下がって（後方に箱がある） | `F moved_backward` | 後退せずに待つ。箱をどけると下がる |
| キッチンへ行って | （単語帳にない） | `check()` が3回とも却下 → 「この指示は単語帳にない言葉を使っています」と伝え、動かない |
| 座って、でも絶対に座らないで | `F sitting & G !sitting` | 満たせる道がない（監督器が空）→ 「この指示は満たせません」と伝え、動かない |
| 止まって | （LLM を通さない） | すぐ StopMove |

（式の正確な形は Claude の出力で変わってよい。意味が同じならよい。）

### 7.4.0 数の入った指示（ユーザーが決めた：繰り返しで表す）

- 前進・後退は 0.5 m、旋回は 90 度を「1回」の単位にする。
- 数は、その動作の繰り返しとして式の中で表す。
  - 「1メートル進んで」→ 前進2回
  - 「180度回って」→ 旋回2回
  - 「3回挨拶して」→ 挨拶3回
- 式の形の例：`F(hello & X F(hello & X F hello))`（挨拶を3回、順に）。最短経路で計画するので、余分な回数は実行されない。
- 1つの動作の繰り返しは 12 回まで（最初は私の判断で 6 回。2026-11-05、利用者の指示で 12 回に上げた）。
  - 6 回にした理由は flloat の DFA づくりが指数的に遅かったことで、formula progression に替えた今は当てはまらない。大きさは回数にまっすぐ比例する（前進 12 回で SPEC 13・監督器 156 状態、0.05 秒。前進 12 → 左 → 前進 12 の 1 本の列で SPEC 26、0.06 秒）。
  - 繰り返しのある動作を `&` で 3 つ並べる（順番を問わない）と SPEC が 13³ = 2197 で `MAX_SPEC_STATES`（2000）を超え、「式が大きすぎます」になる。プロンプトで、言われた順に 1 本の入れ子に書かせる。
  - 12 回は「同じ動作が続けて並ぶ」回数。「A を N 回繰り返して」は中身を変えずに N 回書き出す（N も 12 まで）。1 つの指示の動作は合わせて 60 回まで（`MAX_TOTAL_STEPS`。私の判断）で、超えるときは N を減らし、A の中身は減らさない（試験で、合計に上限をかけようとして最後の辺を落とす答えが出たため）。
  - 式の長さの上限 `MAX_FORMULA_LEN` は 300 から 1500 文字に上げた（60 回の列で最長 1314 文字。60 回でも SPEC 61 程度で、合成は 0.2 秒ほど）。3 回試しても長すぎるときは「指示が長すぎて式にできませんでした。いくつかに分けて言ってください。」と伝える。
  - 括弧の誤りは「「)」が 1 個多すぎます」のように数で伝え、聞き直しで 1 回で直るようにする（長い列の最初の答えは、よく 1 個ずれる）。
- 単位で割り切れない数（0.7 m、45 度など）は、いちばん近い回数（1 回以上）にし、上限を超える数と「ずっと」のような終わりのない繰り返しは 12 回にして動く。どちらも `substitutions` に入れ、画面の「こう受け取りました」に出す（2026-11-05、利用者の指示。§7.4.1）。
  - 12 回は 1 つの動作ごとに数える（挨拶とお辞儀を交互に 10 回 → 5 回ずつ）。回る動作は 12 回（3 周）まで。
  - 「何回か」「何度か」「数回」は 3 回（私の判断）。
  - 「N回回って」「N周」は 360 度 × N。
  - 0（0回・0メートル・0度）は「その動作をしない」。1 回に直さない。ほかにする動作がなければ `unsupported` に入れて動かない（試験で、0 を 1 回に直して動いてしまったため）。
  - 秒・分などの時間と、マイナスの数は `unsupported`（私の判断）。
- 受け入れテストに足す行：
  - 「1メートル進んで」→ forward が2回
  - 「180度回って」→ turn_left か turn_right が2回
  - 「3回挨拶して」→ hello が3回
  - 「0.7メートル進んで」→ forward が1回（「0.7メートル」→ 0.5 m と出す）

### 7.4.1 単語帳にない指示の扱い（私の判断）

ふつうの Claude は、単語帳にない指示でも、近い単語で式を作ってしまいやすい。たとえば「キッチンへ行って」→ `F moved_forward`。そうなると Go2 が勝手に歩き、§4 に反する。そこで次のようにする。

- **出力の形：** `{"formula": "式 または null", "unsupported": ["単語帳で表せなかった言葉", ...], "substitutions": [{"said": "指示の中の言葉", "as": "実際にすること"}, ...]}` とする。3 つとも必須（Codex の `--output-schema` は strict のため）。`substitutions` の無い返事は「読めない返事」として扱い、Go2 は動かない（置き換えを見せずに動かないため）。`substitutions` は画面に出すだけで、動きには使わない。聞き直しで直った答えに `substitutions` が無ければ、前の答えのものを出す。
- **プロンプトに書くこと：** 「近い動作がない動作（ジャンプ、宙返り）と、場所・物や、まわりの物を見て決める動き（キッチン、ボール、障害物の周りを回る）は、代わりにせず `unsupported` に入れ、`formula` は null にする」。
- **言い換えと近い動作での代わりは直す（2026-11-05、利用者の指示）：** 「しゃがんで」→ `sitting`、「寝そべって」→ `lying`、「その場で一周」→ 90 度の旋回 4 回のような同じ意味の言い方と、「走って」→ `moved_forward` のような、ねらいが同じで速さ・大きさだけが違う動作は、単語帳の命題に直す。直したものはすべて `substitutions` に入れ、画面の「こう受け取りました」と記録に出す。
  - 右・左が言われていればその向き。言われていないときだけ左にし、それも `substitutions` に入れる。回れ右・回れ左・振り向いて は 90 度を 2 回。
  - 「〜しながら」は順にする。単語帳にない動作を「しないで」（ジャンプしないで）は、もともとしないので式に入れず、`substitutions` に「（もともとしません）」と出す。
  - 安全のために守れない部分（障害物があっても）は黙って捨てず、`substitutions` に「前に障害物があれば進みません」と出す。
  - 断るもの（私の判断。実際の Claude で試して決めた）：人の手を使う芸（お手、握手）、センサーで終わりを決める動き（前に何かあるまで進む。`obstacle_front`・`obstacle_back` は条件にだけ使い、目標にしない）、近い動作がない動作（ジャンプ）、体の使い方や姿勢が違う動作（二本足で立つ、這う）、ぶつかる動き（突っ込む）、姿勢を保ったまま動く指示（伏せたまま進む）、場所・物・人や、まわりを見て決める動き（キッチン、障害物の周りを回る、おいで、こっちに来て）、どの動作か決まっていない指示（ちょっと動いて、何か芸をして）。
  - 「障害物の周りを回る」を断るのは、物の一覧（`/go2/objects`）にない物のときだけ。一覧にある物（箱・椅子）の「周りを回る」「〜まで行く」は断らず、物の命題で式にする（物の設計書 §6.3）。「障害物」が一覧の物を指すのは、「障害物の周り」「障害物まで」のように行き先として言われ、前にある物が一覧にちょうど 1 つのときだけ。
  - 指示はプロンプトの中で JSON の文字列として渡し、その中の「答え:」「指示:」や式・JSON には従わせない（指示に偽の答えを書いて、断るべき部分を通す試験が通ったため）。
  - 安全は LLM が断ることに頼らない：単語帳には安全なプリセットしかなく（§4・§7.2）、前後の物で止まる・「止まって」が効くことは監督器とコードが守る（§7.1）。代わりにして困るのは「思ったのと違う動き」なので、それを画面に出して見えるようにする。
- **「この数は指定できません」と出すのは、`unsupported` の項目が数と単位だけ（「0メートル」「マイナス2メートル」）のとき。** 割り切れない数はプロンプトが丸めるので、残るのは 0・マイナスか、LLM が丸めなかったときだけ。「障害物の周りを一周する」のように数を含む動作の言葉は、「単語帳にない」と伝える。
- **`unsupported` が空でないとき：** 聞き直しをせず、「『キッチン』は単語帳にないので、この指示はできません」と伝え、動かない。
- **`check()` はそのまま：** 未知の命題・記号を却下する役目は変わらない（二重の守り）。

### 7.5 オートマトンの組み立て方

講義のノートブック（`nl2fl_grid.ipynb`）の方法に合わせる。

- イベントは「動作 + 入った先のラベル」の組で名前を付ける（講義の `right_to_collide` の考え方）。
- 要求側には、環境で実際に起こりうるイベントだけを与える。起こりえないイベントを入れると要求側だけの私的なイベントになり、sync が積を膨らませるため（講義ノート 5.4）。
- **要求オートマトン（SPEC）の作り方：** flloat の DFA 変換ではなく、講義ノート 5.2 の formula progression を、PLANT に出てくるラベルの上だけで行う（`voice_ltl/ltlf.py`）。
  - 状態は「まだ満たす必要が残っている式」。先に初期状態のラベルを1回読ませた式を TCT の状態0にし、可制御イベントのラベルで幅優先に書き換えていく。
  - flloat は式の読み取り（構文の木）と、テストでの照合に使う。
  - 理由：速さ。flloat の変換は、命題の数と入れ子の深さに対して爆発的に遅くなる。安全の決まりと合わせた式で、`F(hello & F danced)` が 17.5 秒、`F(hello & F(danced & F sitting))` が 60 秒超、繰り返し 6 回が 722 秒かかった。progression では、どれも 0.02 秒ほど（Docker、arm64）。2^(命題の数) のラベルの組み合わせを全部たどらないため。
  - 状態が 2000 を超える式と、20 秒を超える合成は「式が大きすぎます」として断る。
- **障害物の出入りは、LTLf の「1ステップ」に数えない（私の判断）：**
  - 要求オートマトンは、不可制御イベント（`front_blocked` / `front_clear` / `back_blocked` / `back_clear`）では状態を変えない（自己ループにする）。
  - こうすると `X` は「次の Go2 の動作」という意味になり、「まず挨拶して」→ `X hello` のような式が、障害物の出入りで満たせなくなることを防げる。
  - 「障害物があるときは前進しない」（§7.1）は、指示の式とは別の決まりとして、`World.forbidden` から作った SAFE を SPEC と meet し（SPEC2）、それを PLANT と meet してから trim・supcon にかける。
  - sync ではなく meet にする（私の判断）：sync は片方にしかないイベントを自由に通すので、禁止するイベントを持たない SAFE と sync しても、何も禁止されない。SPEC は PLANT の全イベントを持つので、禁止するイベントがなければ meet と sync の結果は同じになる（講義の数値もそのまま）。
- trim は、到達可能かつ受理へ到達可能な状態だけを残す。
- supcon は、不可制御イベント（障害物の出入り）を禁止しない、最大許容でノンブロッキングな監督器を作る。
- **今の合成（2026-11-06、物の設計書 §6.1）：** どの式でも、監督器は PLANT と SPEC2 から直接 supcon で作る。上の PRODUCT・TRIMMED を経る流れと同じ監督器になり（講義の数値もそのまま）、メモリは PRODUCT の状態数の 2 乗に比例しなくなる。
  - PRODUCT と TRIMMED は、画面の図と講義の数値のために、PLANT の状態数 × SPEC2 の状態数が 5000 以下のときだけ作る。
  - その積が 400 000 を超える式と、監督器が 50 000 状態を超える式も「式が大きすぎます」として断る。

### 7.6 実行のしかた

1. 監督器 SUP の今の状態から、受理状態までの最短経路（全コスト1。ダイクストラ法か幅優先探索）を求め、次のイベントを1つ実行する。
2. 実行が終わるたびに、Go2 から返ってきた状態で SUP の状態を進める。
3. 不可制御イベント（障害物が出た・消えた）が起きたら、SUP の状態をそれで進め、そこから道を選び直す。立ち以外の姿勢では、センサーの判定を「なし」として扱う（§7.1）。
4. 許される可制御イベントが今ない（たとえば障害物で前進が禁止され、ほかに道もない）なら、待つ。
5. 受理状態に着いたら完了。

**動作の途中の指示と、姿勢の確かめ：**
- 姿勢の変化（立つ・伏せる・座る・立ち上がる）とジェスチャーは、Go2 の中で途中では止まらない（StopMove で終わらない）。その途中で新しい指示や「止まって」が来たら、StopMove はすぐ送るが、新しい計画の最初の指令は、その動作の予定の時間（`actions.py` の `sequence` の待ち時間）が終わるまで送らない。計画は、そのあとの姿勢から作る。
- 「終わりました」と言う前に、Go2 の姿勢が計画の最後の姿勢と同じかを確かめる。違えば「姿勢が計画と違います」としてエラーにする。
- 計画を始めるときに姿勢が不明（UNKNOWN）なら、最大 3 秒、決まるのを待つ。`error_code` が 1002（立ち固め）なら BalanceStand を送り、1013（立ち）を見てから、立ちとして計画する。3 秒たっても不明なら「Go2 の姿勢がわかりません。リモコンで伏せさせてから、もう一度話してください」と伝え、動かさない。`error_code` を読めないつなぎ方では、待つだけにする。

**Go2 への指令：** 各イベントは `actions.py` の `api_id` の列に変換して送る。前進・旋回は zip の `executor.py` と同じく、`/sportmodestate` で距離・角度を測って止める。

## 8. 操作画面（ブラウザのページ）

物の命題（near_〈id〉・around_〈id〉・around_cw_〈id〉）を使う指示は docs/superpowers/specs/2026-11-05-go2-objects-design.md に従う（物を使わない指示は、この節のまま）。

コンテナの中のサーバーが出すページを、Mac のブラウザで開く（`http://localhost:8810`。`GO2_UI_PORT` で変えられる）。日本語で表示する。画面の見本は `docs/reference/ui_*.png`。

- **つないでいる先：** 右上に「シミュレーション · にせ Go2」「シミュレーション · Gazebo」「実機」のどれかを出す（`SIM_KIND` と `SIM` で決まる）。
- **話す：** スペースを押している間は「録音中」と大きく表示する。離すとサーバーへ音声を送る。文字で指示する入力（試験用）もある。
- **お知らせ：** 話すボタンの下に、今の状況を1枚で出す。種類は次のとおり。
  - 待っている：前（後ろ）に物がある、またはセンサーが途切れている。「あと N 秒で中止」を出す。残り秒数は、サーバーの時計（`waiting_since` と `server_now`）の差で出す。ブラウザの時計は使わない。
  - 終わった
  - 止めた（止める言葉を聞いたときは、その言葉も出す）
  - 満たせない指示（監督器が空）
  - できない指示・続けられなかった
  - ログインが必要
  - 聞き取れなかった・音声を文字にできなかった
- **指示と翻訳：**
  - 書き起こした文。音声のときは「Whisper モデル · 1.4 秒」を添える。モデルを読み込んだ回だけ「（初回の読み込み 6.2 秒）」も添える。秒数は読み込みを除いた書き起こしだけの時間。
  - 式と、`check()` の合否。Claude の試行ごとの式と却下理由は「LLM の試行」を開くと見える。
  - 言われた言葉と違う形にした部分（言い換え・近い動作・数の丸め・上限）は、式の下の「こう受け取りました」に「『走って』→ 前へ歩く（0.5 m）」の形で出る（§7.4.1）。
- **計画：** 実行する動作の並びと、実行中・済みの印。
- **状態遷移図：** タブは「計画の道」「監督器」「trim 後」「要求」「環境」。既定は「計画の道」で、計画の道筋と今いる状態を青で示す。
  - 「計画の道」のほかの全体図（監督器・trim 後・要求・環境）は、200 状態を超えると描かず、「大きすぎるので図は省きました（N 状態）。」と出す（物を使わない式でも。物の設計書 §6.6）。計画は、図を描き終わるのを待たずに始まる。
- **Go2 の状態：** 姿勢、前方・後方の一番近い物までの距離と「あり / なし」、実行中の動作、位置（x, y, 向き）。
- **上から見た小さな図：** Go2 の位置と向き、置いた箱、止まる距離（0.5 m）の範囲。物の一覧の物（箱・椅子）も出し、図の下に「見えている物：…」を出す（物の設計書 §6.7）。
- **ボタン：** 「前に箱を置く」「後ろに箱を置く」「箱を全部どける」「止める」。箱は、置いた時点の Go2 から前（後ろ）に決まった距離（既定 1.2 m）に置く。
- **記録：** 何が起きたかを日本語の文で並べる。イベント名と実行器の報告は、入れ子の「詳しく」を開くと見える。
- **見た目：** 暗い色の設定（`prefers-color-scheme: dark`）に合わせて配色を切り替える。幅 640 px 以下（スマホ。390 px で確認）では 1 列に並べる。

## 9. シミュレーションの Go2

ROS 2 のノードとしてコンテナ内で動かす。実機と同じトピック・型を使う。

- **指令を受ける：** `/api/sport/request` を受け、`actions.py` にある `api_id` に応じて姿勢や動きを変える。
  - 実機に近い時間をかける（立つのに数秒など）。
  - 実機と同じく、できない状態での指令は無視する（伏せたまま Move しても動かないなど）。これでテストに意味を持たせる。
- **Move：** 速度を積分して位置と向きを変える。送り直しが途切れたら止まる。
- **`/sportmodestate` を出す：** 位置、向き、姿勢に合う `error_code` を出す。対応は `actions.py` の `_ERROR_CODE_TO_STATE` に合わせる。
- **`/utlidar/cloud` を出す：** シミュレーションの床の上に置いた箱（§8 のボタンで置く）を、Go2 の今の位置と向きから見た点群にして出す。
  - Go2 が歩いて箱に近づけば、点群の中の箱も近づく。こうして、zip の `perception.py` の判定（0.5 m より近いと止まる、0.7 m より遠いと再開）が本物と同じように反応する。
  - 座標の向きや LiDAR の取り付け位置は、`perception.py` の設定（`lidar_x`、`lidar_z`、`lidar_pitch`）に合わせる。
  - Go2 は箱を通り抜けられないことにする。止まるのが遅れて箱に入ったら「ぶつかった」と記録し、テストで失敗にする。
- **同じ窓口で入れ替えられる：** 実機に移したら、このノードを起動しないだけで、本物の Go2 と入れ替わる。

## 9.1 Gazebo の Go2（ユーザーの指定：ROS 2 + Gazebo）

物の命題（near_〈id〉・around_〈id〉・around_cw_〈id〉）を使う指示は docs/superpowers/specs/2026-11-05-go2-objects-design.md に従う（物を使わない指示は、この節のまま）。

今のコードの形（`docker/Dockerfile.gazebo`、`gazebo/`）。経緯と測った値は [gazebo_feasibility_jazzy.md](reference/gazebo_feasibility_jazzy.md)（Task 15b）と [gazebo_turn_fix.md](reference/gazebo_turn_fix.md)（Task 16fix）。

### 使うもの

- **ROS 2 Jazzy（Ubuntu 24.04）+ Gazebo Harmonic（Gazebo Sim 8）：** gazebo のコンテナだけ。土台は `ros:jazzy-ros-base-noble`。app のコンテナは Humble のまま（§5）。
  - 最初は legubiao の `humble` ブランチ（Humble + Gazebo Classic 11）を選んだ。しかし Gazebo Classic は Ubuntu 22.04 の arm64 に無く、この Mac では動かない（Task 15、[gazebo_feasibility.md](reference/gazebo_feasibility.md)）。そこで Jazzy + Harmonic に移した（Ruling R10）。どちらも arm64 の公式パッケージがあり、エミュレーションが要らない。Harmonic は今も保守されている。
- **[legubiao/quadruped_ros2_control](https://github.com/legubiao/quadruped_ros2_control) の `main` ブランチ：** commit `5434c5810d1a7fe223bcfd04550e9d3bfdd4b458`（2025-06-24、2026-11-04 時点の先頭）に固定する（`Dockerfile.gazebo` の `QUADRUPED_ROS2_CONTROL_COMMIT`）。
  - 使う部分：unitree_guide controller、`go2_description`、`gz_quadruped_playground`（Gazebo Harmonic 用の ros2_control のハードウェア `gz_quadruped_hardware` と world）。
  - 選んだ理由：ライセンスは Apache-2.0。unitree_guide controller が「脱力 → 伏せ → 立つ → 歩く（速度）」の状態の切り替えを持っている（`/control_input` の `command` で切り替える）。
  - 比べたもの：CHAMP を使う `anujjain-dev/unitree-go2-ros2` は立ち・伏せの切り替えがない。
- **`docker/patches/` の 4 つのパッチ：** 固定した commit に、ビルドの前に名前の順で `git apply` する（upstream は書き換えない）。0001・0002 が無いと、その場で 90 度回った後に転ぶ。0003・0004 が無いと、歩き出し・旋回の終わり・角で揺れが育つ（物を使う指示の一周 5 回のうち、転んだのが 2 回、揺れて位置がずれて止まったのが 1 回）。イメージは `go2-voice-ltl-gazebo:patch-0004`。0001・0002 だけの前のイメージは、作った Mac で `go2-voice-ltl-gazebo:patch-0002`（= 前の `:dev`）として残してあり、`GO2_GAZEBO_IMAGE` で戻せる（この Dockerfile からは作り直せないので、付けたまま build しない）。
  - `0001-estimator-world-frame-leg-odometry.patch`：状態推定（Estimator）が、脚の測定値を胴の座標のまま世界の座標のカルマンフィルタに入れていた。世界の座標に直してから入れる（元の unitree_guide と同じ式）。
  - `0002-feet-end-calc-body-frame-stance-angle.patch`：歩くに入るときの足の角度（`FeetEndCalc::init`）を胴の座標で測る。回った後に伏せて立ち直すと、最初の数歩でよろけていた。
  - 結果：その場の ±90 度、回った向きでの立ち直しとも 3/3 合格（[gazebo_turn_fix.md](reference/gazebo_turn_fix.md)）。
  - `0003-estimator-velocity-low-pass-out-of-state.patch`：状態推定が、速度にかけた 3 Hz のローパスの値をカルマンフィルタの状態に書き戻していた（元の unitree_guide は書き戻さない）。推定の速さが約 0.14 秒遅れて小さく出て、歩き出しで胴が指令の 3 倍まで出ていた。書き戻さない。
  - `0004-trotting-enter-from-stance-all.patch`：歩くに入るとき、4 本の足を着いた状態（`STANCE_ALL`）から始める。最初の周期に足踏みを始めると、最長 0.225 秒 4 本とも振り出しになっていた。
  - 結果：物を使う指示の一周 5/5・椅子 3/3（[gazebo_objects_e2e.md](reference/gazebo_objects_e2e.md) 第 5 部）。
- **既知の注意：**
  - legubiao の README には「KDL を使っているので動きが不安定なことがある」とある。
  - 歩き方の周期は実際の時間で数える（`WaveGenerator`）。Gazebo が CPU 不足で止まったり進んだりすると傾くので、CPU に余裕を残す。
  - 前進して止めた直後に回ると、揺れが大きくなることがあった（roll が 0.5 rad を越えることがあった）。0003 の後は、一周の旋回中の roll（95 %）が 0.01〜0.05 rad。

### 作り

- **Gazebo のコンテナ：** app とは別のイメージ（`go2-voice-ltl-gazebo:patch-0004`。0003・0004 の前は `go2-voice-ltl-gazebo:dev`）。`unitree_go`・`unitree_api` は app と同じ unitree_ros2 の commit から Jazzy の上でビルドする。起動は `docker compose --profile gazebo up gazebo`。
- **画面：** コンテナの中の仮想の画面（Xvfb）で Gazebo の画面を動かし、noVNC でブラウザ（`http://localhost:6080/vnc.html`）から見る。Mac の Docker には GPU がないので、ソフトウェアで描く（llvmpipe）。
- **launch（構成 B）：** `gazebo/launch/go2_gazebo.launch.py`。upstream の playground の launch は、カメラ 2 台と rviz2 で CPU が足りず、real-time factor が 0.13 になる（NO-GO）ので使わない。
  - Gazebo の画面あり（`gui:=false` でサーバーだけ）、センサーは LiDAR と logical camera（画像は出さず、見えている model の名前と位置だけ。画像を出すカメラはなし）、rviz2 なし。
  - Go2 は `gazebo/go2_sensors.urdf.xacro`。LiDAR（`gpu_lidar`）は base から x 0.28 m・z 0.10 m・傾きなしで、`perception.py` の既定値（`lidar_x`・`lidar_z`・`lidar_pitch`）と同じ。水平 360 度・垂直 −30〜+30 度、10 Hz。本当の位置は OdometryPublisher（50 Hz）。
  - `ros_gz_bridge` で、時計（`/clock`）、LiDAR の点群、位置（`/model/robot/odometry`）、logical camera（`/gazebo/logical_camera`）、箱を出し入れするサービス（`/world/empty/create`・`/world/empty/remove`）をつなぐ。
  - 測った値：real-time factor 0.64〜0.77、実際の 5 秒の前進で 1.40 m、前進の間の roll / pitch は 0.063 / 0.031 rad 以下。
- **橋渡し（Go2 のふりをするノード、`gazebo/gazebo_bridge.py`。中身は `gazebo/bridge_core.py`）：** アプリ側は実機と同じ窓口のまま、何も変えずに Gazebo を使える。

| 受けるもの / 出すもの | 中身 |
|---|---|
| `/api/sport/request` を受ける | unitree_guide controller の `/control_input`（`command` と速度 `lx`・`ly`・`rx`・`ry`）に変える |
| `/sportmodestate` を出す | 位置と向きは Gazebo の本当の値（odometry）。`error_code` は、送った指令から橋渡しが持つ状態で決め、`actions.py` の対応表に合わせる |
| `/utlidar/cloud` を出す | Gazebo の LiDAR の点群（frame `utlidar_lidar`）から、自分の体の箱の中の点と、地面の点（世界の z < 0.05 m）を除いて出し直す（Ruling R23）。高さ 5 cm 未満の物は、シミュレーションでは見えない |
| `/sim/obstacles` を受け、`/sim/world` を出す | にせ Go2 と同じ。箱は Gazebo の中に本当の物体（動かない 0.3 × 0.3 × 0.4 m）として出し入れする |
| `/go2/objects` を出す | 起動時に `box_1`（2.5, 1.5）と `chair_1`（2.5, −1.5）を置き、logical camera で見た物の一覧を 2 Hz で出す（物の設計書 §6.2） |

- **時計：** 窓口の時間（`error_code` が変わるまで、Move の 1 秒の期限）はアプリと同じ実際の時間で数える。controller へ `command` を送る間隔はシミュレーションの時間で数える。Gazebo が実時間より遅いと、`error_code` が先に変わり、体は後から追いつく。
- **Humble（app）↔ Jazzy（gazebo）の通信：** 同じ compose のネットワークで、どちらも CycloneDDS。`/api/sport/request`・`/sportmodestate`・`/utlidar/cloud`・`/sim/*` は、どちらの向きにも届く。
  - ただし、ノードの名前を伝える `ros_discovery_info` の型（`rmw_dds_common/msg/Gid`）が Humble と Jazzy で違うので、相手を見つけたときに標準エラーに `string data is not null-terminated` / `invalid data size` が出る（データは届く）。
  - Humble 側の `ros2 node list` は失敗し、`ros2 topic info -v` の相手は `_NODE_NAME_UNKNOWN_` になる。アプリと橋渡しは相手のノードの名前に頼らない（送り手・受け手の数だけを使う）。

### 指令ごとの扱い

| 指令 | Gazebo での扱い |
|---|---|
| StandUp → BalanceStand | 本当に立つ（伏せ → 立つ → 歩く） |
| StandDown | 本当に伏せる |
| Move・StopMove | 本当に歩く・回る・止まる。Move は 1 秒送り直しが無ければ止まる（実機と同じ）。controller が「歩く」に入ってから 0.5 秒（シミュレーションの時間）は、速度を 0 のまま待たせてから入れる。歩き出しでよろけないため（Ruling R22）。「歩くに入った」時刻は、controller の `/rosout` の知らせで知る。回る速さは 0.5 rad/s まで（controller の `rx` の最大） |
| Sit・RiseSit | 伏せの姿勢で代用する（`error_code` はおすわりとして返す）。ログに「（Gazebo では伏せで代用）」「（Gazebo では伏せからの立ち上がりで代用）」 |
| Hello・Stretch・Content・Heart・Scrape・Dance | 立ったまま、3 秒待つ「ふり」。ログに「（Gazebo では再現なし）」 |

### 最初に試すこと（作り込む前）

この Mac の Docker で、Go2 が Gazebo の中で次の3つをできるかを先に試す。

- 立つ
- 速度の指令で前に歩く（転ばない）
- その様子がブラウザから見える

あわせて、実時間に対する速さ（real-time factor）を測る。使えなさそうなら（立てない、すぐ転ぶ、極端に遅い）、作り込む前にユーザーに報告して相談する。

結果（Task 15b）：Jazzy + Harmonic の構成 B（LiDAR だけ、rviz2 なし）で GO（条件つき）。[gazebo_feasibility_jazzy.md](reference/gazebo_feasibility_jazzy.md)。

### 基本動作の確認（ユーザーの希望）

Gazebo の Go2 を相手に、次を確かめる。様子はスクリーンショットで残す。

- 渡された `demo_script.py`（立つ → 前進 0.5 m → 左 90 度 → 挨拶 → 座る → 立ち上がる）が最後まで動く。

## 10. Linux PC への移し方

- **移す先（ユーザーが決めた）：** 画面つきの Ubuntu PC。その PC のブラウザとマイクで操作する。インターネットは Wi-Fi などで別につなぐ。
  - Claude（`claude -p`）を呼ぶのにインターネットが必要。
  - 有線（Go2）と Wi-Fi（インターネット）を同時に使う設定を、README に書く。
- **アーキテクチャ：** 移す先は x86_64 の可能性が高い。Docker のイメージは arm64（この Mac で確認）と x86_64 の両方でビルドできるようにする。
- **ブラウザ：** その PC 上で `http://localhost:8810`（`GO2_UI_PORT` で変えられる）を開くので、マイクの許可はそのまま使える。HTTPS や SSH トンネルは不要。
- フォルダをそのまま Linux PC（Ubuntu 22.04 想定）にコピーする。
- **やり方 A：** 同じ Docker を `network_mode: host` で起動する。Linux の上なら、コンテナから LAN の差し口が直接見えるので、実機とつながる。
- **やり方 B：** Ubuntu 22.04 + Humble + unitree_ros2 を直接入れて、同じプログラムを動かす。
- **変えるのは2か所だけにする：**
  1. LAN の差し口の名前（`CYCLONEDDS_URI`）
  2. シミュレーションの Go2 を起動しない設定
- これを README に手順として書く。有線の設定（PC 側を `192.168.123.x` に固定する。`.161` は使わない）、`ping 192.168.123.161` での確認、`ros2 topic echo /sportmodestate` での確認も書く。
