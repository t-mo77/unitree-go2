# Go2 Objects (Gazebo box and chair) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 「箱の周りを一周して」「椅子まで歩いて」 work by voice. Gazebo (and the fake Go2) publish the objects the front camera sees. Claude writes formulas with per-object propositions. A grid PLANT and its supervisor are synthesized for those formulas, and a closed-loop grid executor walks the plan. The page shows the objects, the cells and the path.

**Architecture:**
- A standard-library-only module, `voice_ltl/objects.py`, holds the shared parts: the object row, the frozen Scene, the proposition names, the user-facing copy and the `/go2/objects` JSON. Every other task codes against it.
- Formulas with object propositions use a new grid plant (`voice_ltl/grid.py`). It is synthesized with the memory-safe `supcon(PLANT, SPEC2)` and run by `GridExecutor`, with a snap-and-jump after every step.
- Formulas without object propositions keep `go2_world` and the zip's Executor, unchanged.
- Gazebo gets a logical camera and spawns `box_1` and `chair_1`. The Gazebo bridge and the fake Go2 both publish `/go2/objects` (`std_msgs/String` JSON, odom frame).

**Tech Stack:**
- Python 3.10 (app, ROS 2 Humble) and 3.12 (Gazebo bridge, Jazzy)
- pitct 1.0.8, flloat 0.3.0, graphviz
- FastAPI, plain JavaScript on a canvas
- Gazebo Harmonic logical camera and ros_gz_bridge
- pytest, plus the node 22 harness in `tests/test_server.py`
- docker compose

**Spec:** `docs/superpowers/specs/2026-11-05-go2-objects-design.md` (called "the design" below). Read it together with these:
- `.superpowers/sdd/2026-11-05-go2-objects/builder-check.md`: its 30 resolutions are adopted as Rulings R1–R30.
- The maps in the same folder: `map-automata.md`, `map-gazebo.md`, `map-language.md`, `map-motion.md` and `map-ui.md`.
- The parent design, `docs/design.md`.

## Review Focus

These failure modes are the most likely to bite a person and are not covered by any one task's main tests. Each has a test in the task that owns the code.
1. **A second instruction after a lap.** The Go2 is no longer at the origin and its yaw is not 0. The grid is anchored to that pose and the plan is still right. Tests: `test_second_instruction_from_where_the_lap_ended` (G) and `test_rotated_anchor_gives_the_same_cells` (B).
2. **Speaking before `/go2/objects` has arrived** (Gazebo just started). The page says 「見つかりません」, and the same words work once the list arrives. Test: `test_objects_arriving_after_a_refusal_work_on_the_next_instruction` (G).
3. **A stop or a new instruction in the middle of a grid plan.** StopMove is sent and the session goes idle. The next instruction without objects uses the 12-state plant. Test: `test_stop_mid_lap_then_a_plain_instruction` (G).
4. **A box put on the route** (the page's 「前に箱を置く」) during a grid plan. The Go2 does not collide; it waits or takes another way. It never stops with 「監督器がセンサーの変化を受け付けませんでした」. Test: `test_box_on_the_route_during_a_grid_plan` (G).
5. **Two objects with the same label.** The message is 「…決められません」. With the directions in `## Objects`, 「右の箱」 can pick one. Tests: `test_two_boxes_are_ambiguous` (C) and the Task J refusal group.

## Rulings

Rulings R1–R30 adopt the builder check, item by item, as decisions. Each gives the ruling, why, and what it costs if it is wrong.

- **R1 Sensor bits only while standing.** Lying and sitting states have no bits; the 4 sensor events are uncontrollable self-loops there. `stand` and `rise_sit` land with bits (False, False); `lie_down` and `sit` drop them. In grid mode, `_complete` sets `_sensed` to the new plant state's bits. *Why:* the session fires sensor events from the actual posture while the plant is still lying (a stand takes 4 s). *If wrong:* an abort during `stand` (G's tests would catch it).
- **R2 Scene and anchor are taken at different times.** The Scene (objects and pose) is frozen at `_accept_text`; the prompt, `check()` and the directions use it. The grid anchor is `link.pose()` at the `_get_ready` tick, sent as the payload `(tr, initial, pose)`. A formula with object atoms and no pose gives `MSG_NO_POSE`. *Why:* this makes "cell (0, 0), heading 0" literally true. *If wrong:* the grid is off by however far the Go2 moved between the instruction and the start.
- **R3 Size and radius.** `size` = [extent along odom x, extent along odom y]. It is never null; the default for both labels is [0.5, 0.5] until the LiDAR measures it. Everywhere, r = hypot(sx, sy) / 2. *Why:* then r + 0.45 also covers the Go2 turning in place. *If wrong:* a smaller r lets plans pass inside the turning radius.
- **R4 Near band.** A near cell has r + 0.75 ≤ d ≤ min(r + 1.5, 1.4 m) and |heading − bearing| ≤ 40°, and depends only on (cell, heading). *Why:* the design §2 asks for 1.5 m and 45° at the stop; this leaves 0.1 m and 5° for the end error. *If wrong:* a wider band fails the acceptance.
  - An object with r > 0.65 m (larger than about 0.92 × 0.92 m) has an empty band. Its `near_<id>` is never true, so 「〜まで歩いて」 gives `MSG_NO_PATH` (R15). This is accepted for the first step, where both objects have r ≤ 0.36. G3 has a test for it.
- **R5 Blocked cells stay at r + 0.45.** The 0.6 m edge check in §2 applies to the §2 scenario: a fresh start with the default layout. Other tests assert that the body centre stays at least r + 0.35 from the object centre. *Why:* guaranteeing 0.6 m for any layout would need larger blocked cells and would leave little free space. *If wrong:* an object off the lattice gets about 0.45 m of edge clearance (still no contact).
- **R6 Lap progress.** Sectors are in the grid frame, measured from the object centre to the cell centre: E [−45°, 45°), N [45°, 135°), W [135°, 225°), S [225°, 315°). The move rule is `next_lap` (Task B). The clockwise prop mirrors it. Only reachable states are built. *Why:* the rule needs the previous sector, and the source cell already gives it, so no extra state is needed; the winding inside the ring is exactly +1. *If wrong:* the other encodings cost about 5 times the states.
- **R7 Blocking.** Every Scene object, seen now or remembered, blocks the cells it covers inside the grid. Labels exist only for the formula's atoms. The rectangle comes from the robot and the referenced objects. The start cell is never blocked. No move enters a blocked cell. *Why:* the design §4 forbids entering any object's cells, and 「椅子まで」 could otherwise route through the box. The start-cell exemption avoids an invalid initial state. *If wrong:* a plan passes through an object that is not in the formula, and only the LiDAR stops it.
- **R8 Rectangle.** For each referenced object, take the cells whose centres lie within its outer band on each axis (near: min(r + 1.5, 1.4); around: r + 1.75). Add the robot's cell, then a 1-cell margin. The cap is 256 cells of area. Checks run in this order: an object over 6 m away gives 遠すぎます, then an area over 256 gives `MSG_TOO_SPREAD`. The Gazebo lap is 12 × 11 = 132 cells; the lap plus the chair is 12 × 15. *Why:* 16 cells per side cannot keep the 6 m promise (an object 6 m ahead needs up to 19 cells along x); a cap on the area keeps the same state budget. *If wrong:* objects 5–6 m away are refused, or plants grow too big.
- **R9 Synthesis guards.**
  - PRODUCT and TRIMMED are built only when `len(states) * |SPEC2| ≤ 5000`.
  - Synthesis is refused before pitct when `len(states) * |SPEC| > 400 000`.
  - It is refused after supcon, before any read, when `statenum(SUP) > 50 000`.
  - `check_time` runs after supcon, after each read and after the pairs.
  - `_read` uses the fast path.

  *Why:* memory and time are bounded before the expensive steps, and the TRIMMED tab and the lecture numbers stay for small cases. *If wrong:* an out-of-memory kill (today's latent formula) or a missing tab.
- **R10 Jump.** `Synthesis` keeps the World and `sup_pairs`. When the snap differs from the plan, the observed state is computed as follows:
  - It is the action from the planned source, landing in the snapped (cell, heading), with the planned posture and bits and the lap rule applied.
  - The event comes from the observed label, and spec' = δ(spec of the current SUP state, event).
  - If SUP has the pair (observed, spec'), the runtime jumps there; otherwise the Go2 stops.

  *Why:* many cells share an event name, so `apply` alone would silently follow the planned cell. *If wrong:* the supervisor believes the Go2 is somewhere it is not.
- **R11 Snap.** The Go2 stops when the offset is over 0.3 m **or** the yaw error is over 30°.
  - `GridExecutor` ends a move at along ≤ 0.03 m (or |yaw error| ≤ 3° for a turn), sends StopMove, waits `GRID_SETTLE_S` = 0.5 s, and then reports done.
  - The snap uses that tick's pose and runs after every Step.
  - SENSOR_LOST on that tick defers the completion; `block_timeout` applies.
  - `MSG_POSITION_DRIFT` is an error whatever the status.

  *Why:* Gazebo and the real Go2 coast 0.05–0.10 m and 3–5° after StopMove, and snapping a moving robot gives false jumps. *If wrong:* spurious stops or jumps.
- **R12 GridStep.** `GridStep(Step)` keeps `value = step_value(action)` for the log text and the timeout, and carries `goal_xy` and `goal_yaw` in odom. `GridExecutor(Executor)` lives in `voice_ltl` with its own ExecConfig (turn speed 0.5). The session keeps both executors and uses the active one everywhere. The param names stay `"distance"` and `"angle"`. *Why:* the session's log rewriting (`_in_words`) and the executor's SENSOR_LOST hold depend on `Step.text` and on these names. *If wrong:* the log shows raw event names, or a move is not held when the sensors drop.
- **R13 The plan does not wait for drawings.** The outcome is queued with `diagrams={}`. The worker then draws and queues a second item, which is applied only if `self.synthesis is syn`. `test_sup_drawing_does_not_block_tick` waits for the diagrams before it reads `v_start`. *Why:* the design §6.6 says the plan starts first, and dot on a big automaton takes minutes. *If wrong:* the Go2 waits for drawings.
- **R14 Large diagrams.**
  - Above 200 states, `render_svg` returns a placeholder and never calls dot.
  - For a grid synthesis, the placeholder adds 「上から見た図を見てください」.
  - A missing TRIMMED gets the placeholder too.
  - `_redraw_sup` does not redraw SUP above the cap.
  - `_sup_highlight` uses `Runtime.walk`.

  Large SUPs of formulas without objects lose their full drawing; the motion is unchanged. *Why:* graphviz did not finish in 120 s on a 1600-state PLANT. *If wrong:* only drawings are lost.
- **R15 No path.** The message is `MSG_UNSATISFIABLE + NO_PATH_REASON` when SUP is empty **and** some object atom of the formula appears in no reachable label. `message_kind` uses `startswith(MSG_UNSATISFIABLE)`. *Why:* an equality check would turn the message with its reason into a generic error notice. *If wrong:* the wrong notice and icon.
- **R16 Messages for unsupported object words.** For an unsupported item that holds a label word, the number of objects with that label in the Scene decides: 0 gives 見つかりません, 2 or more gives 決められません, and exactly 1 gives today's 単語帳 message. *Why:* one fixed message per case, with no schema change; 障害物 and 周り are not label words, so `test_session.py:188` still passes. *If wrong:* a misleading reason (「見つかりません」 when there are two boxes).
  - Plan review: an item that also holds an object-handling verb (持, 押, 運, 拾, 動か, どけ, どか) is never an object item. 「箱を持つ」 keeps today's 単語帳 message whatever the count, because the design §3 leaves holding and pushing out, and §6.3 gives 見つかりません only when the item is the object's name.
  - When every item became an object message, today's 「「この指示」は単語帳にない…」 sentence is not added.
- **R17 「障害物」.** It names a listed object only as the target of 周り, まで or のところ, and only when exactly one listed object's direction contains 前. Otherwise it goes to `unsupported`. Conditions keep `obstacle_front` and `obstacle_back`. *Why:* in the default layout both objects are in front, and 「前に障害物があったら」 must keep its LiDAR meaning. *If wrong:* the Go2 circles the wrong object.
- **R18 Directions.** From the start pose, box_1 is 左前 (+31°) and chair_1 is 右前. The words come from 8 sectors of 45°. The distance is from the base centre to the object centre, rounded to 0.1 m. `objects.where` is the only place that computes them. *Why:* odom y points left (REP-103), so the design's examples had 左 and 右 swapped, and 「右の箱」 must pick the box the camera sees on the right. *If wrong:* left and right are swapped on the page and in the prompt.
- **R19 Prompt layout.**
  - A `### 物` subsection goes before `### 断るもの`.
  - The refusal line is rewritten so that every pinned substring stays.
  - The object examples are separate (`_OBJECT_EXAMPLES`, with `EXAMPLE_SCENE`).
  - `## Objects` sits between Vocabulary and Rules, and the object propositions are added to Vocabulary.
  - Query stays last.

  *Why:* this keeps every prompt pin (`test_grammar_translator.py`, `test_session_safety.py`) and design.md §7.4.1 (left by default, every substitution shown). *If wrong:* pinned tests fail, or the LLM writes a lap as turns on the spot.
- **R20 What the Scene holds.**
  - The Scene holds every valid row, seen now or not; the prompt marks 「（いまは見えていません）」.
  - The wire list is not capped. The 8 nearest objects go into the prompt, the vocabulary and the check; all objects block cells.
  - The Go2 card lists only `visible: true` rows.
  - `RosLink.objects()` returns [] when nothing arrived for 2.0 s.
  - `seen` is never compared with the app's clock.

  *Why:* the objects are static (§3), and sim time versus wall time makes clock arithmetic unreliable. *If wrong:* objects are forgotten, or a stale list is used.
- **R21 Validation.** A row is kept only when:
  - `id` matches `^(box|chair)_[1-9][0-9]?$`,
  - `label` is the id's prefix,
  - x and y are finite and the size is above 0,
  - and the message frame is `odom`.

  Everything else is dropped, in one place (`objects.parse_rows` / `objects.parse`). *Why:* the names stay flloat-safe (lowercase, fixed prefixes, never starting with a keyword), and detector text never reaches the prompt. *If wrong:* unreadable formulas, or a prompt injection through an object name.
- **R22 Objects in the simulator.**
  - `SimGo2.objects` is separate from `boxes`: it takes part in collisions and the LiDAR, but not in `/sim/world` or `clear_boxes`.
  - A pure fake camera has a memory. `DirectSimLink.objects()` works on demand.
  - `fake_go2` publishes at 2 Hz with `time.time()` stamps.
  - The default layout and the topic live in `objects.py` (P1).

  *Why:* inside `boxes`, the chair would be drawn as 「箱」 and removed by 「箱を全部どける」, and existing tests would see new LiDAR points. *If wrong:* existing simulator tests break.
- **R23 Gazebo models.**
  - box_1 is a static 0.5 × 0.5 × 0.5 cube with its origin at its centre (spawn z 0.25).
  - chair_1 has a 0.45 × 0.45 seat with its top at 0.45 m (the origin; spawn z 0.45), 4 legs, and a backrest up to 0.9 m on −x.
  - The logical camera sits on its own link at `CAMERA_IN_BODY`: near 0.1, far 8, hfov 2.094, aspect 1.778, 5 Hz.
  - Models are filtered by the R21 regex. They are spawned once, and "already exists" counts as present.
  - The RTF is measured again and must stay at least 0.6.

  *Why:* a reproducible world, and the vertical field of view keeps both origins in view, lying or standing. *If wrong:* objects are missing from the list in Gazebo (Task I would show it).
- **R24 Tools.** `run_formula` pre-checks object propositions and waits up to 3 s for the ids. `gazebo/tools/objects_check.py` prints the §2 measurements as JSON. *Why:* the §2 check is measured without the LLM and can be repeated, the same way `turn_check.py` works. *If wrong:* there is no evidence for §2.
- **R25 Labels.** label(dst, action) = (atoms ∩ {posture, action and object props}) ∪ {obstacle_front, obstacle_back, moved_forward, moved_backward when true at dst}. `event_name` is unchanged, so an event such as `stand_to_` is allowed. Every state is marked. `forbidden` comes from `UNSAFE_LABELS`. States are indexed with a dict. *Why:* the fewest events (map-automata finding 4: 176 events instead of about 560), and SAFE stays equivalent to `SAFETY_FORMULA`. *If wrong:* a bigger SPEC and SAFE, and slower synthesis.
- **R26 Planner.** The planner stays BFS with the R14 tie-break. Only `jump` and `walk` are added. *Why:* the lecture route in `test_planner.py` stays, there is one planner for both worlds, and taking backward out of the grid removes the bad routes. *If wrong:* some routes turn first where a person would walk first (they are still the shortest).
- **R27 Snapshot.** The shapes are below. While a grid exists, the view is frozen per synthesis. The new colour token is `--map-blocked`. All of it is computed at synthesis and in `_refresh_plan`, never in `snapshot()`. *Why:* one shape serves both the page and the node tests, and the snapshots at 5 Hz stay cheap. *If wrong:* the page and the server disagree.
- **R28 Memory tests.**
  - (a) A synthetic 8 × 8 grid with hello × 12, in a child process: under 5 s and `ru_maxrss` under 1 GB.
  - (b) A slow test: the latent go2 formula gives TOO_BIG within `timeout_s` + 5 s.

  *Why:* these test the §4 failure conditions (memory, 30 s). The design's "1 s" cannot hold for the latent formula, whose progression alone takes about 20 s. *If wrong:* flaky time limits.
- **R29 Real-Claude trials** are a script (Task J). It uses a synthetic default Scene and compares plans with reference formulas. *Why:* this accepts equivalent phrasings and rejects a wrong object or direction. *If wrong:* the trials are miscounted.
- **R30 Parent design.** `docs/design.md` gets a pointer to this design for formulas with object propositions. *Why:* the parent still refuses 「障害物の周りを回る」 and describes only the 12-state plant. *If wrong:* the next builder reads two contradicting specs.

Plan-level rulings:
- **P1 One shared module.** The shared constants, copy, topic name and default layout live in `voice_ltl/objects.py`. (The builder check put the layout in `sim_core` and the topic in `ros_link` and `gazebo_bridge`.)
  - *Why:* otherwise the parallel tasks D and E would import from each other's files. `objects.py` uses only the standard library, so Jazzy can import it.
  - `ros_link.py` re-exports `OBJECTS_TOPIC`, because `fake_go2` takes its topic names from `ros_link`.
  - *If wrong:* one import line moves.
- **P2 `Link.objects()` returns validated wire rows** (`list[dict]`, design §6.2). `RosLink` validates with `objects.parse`, and the Session runs `objects.parse_rows` again (it is idempotent). *Why:* this keeps the design's signature, and links that do not validate (test links) are still safe. *If wrong:* nothing but a second cheap pass.
- **P3 The new error copy lives in `objects.py`.** `MSG_NO_POSE`, `MSG_POSITION_DRIFT`, `MSG_TOO_SPREAD` and `NO_PATH_REASON` are there, so Task F can add `NOTICE_KINDS` rows in wave 1, before Task G uses them in `session.py`.
- **P4 What counts as one lap (controller ruling C1, 2026-11-06, replaces the 4-step rule).** The lap closes: `around_<id>` becomes true when the progress reaches `LAP_DONE = 5`, that is on the 5th counter-clockwise sector crossing after entering the ring, so the Go2 passes the sector where it entered and the swept angle is 360°–450°. `grid.LAP_DONE = 5` is exported. The acceptance is 0.9 ≤ winding < 1.5 for measured paths (the approach from the start adds a little) and 0.95 ≤ w for the BFS path over cell centres. The clockwise prop mirrors it (−1.5 < w ≤ −0.9). *Why:* with 4 crossings the shortest plan enters near a sector's end and stops after about 270°, on the far side of the box; a person who asked for 「一周」 sees three quarters of a lap. *If wrong:* about one more sector of walking (1–2 m) and about 20 % more ring states.
- **P5 Early refusal of far objects.** The translator also refuses an object more than 6 m from the frozen Scene pose, so the Go2 does not stand up first. `grid_world` checks again from the anchor.
- **P6** `msg_ambiguous` uses the real count n (「2 つ」 for two). *Why:* with three boxes, 「2 つ」 would be false. *If wrong:* only the wording changes.
- **P7 GridExecutor gains:**
  - yaw gain k_yaw 1.5 /s and cross-track gain k_cross 1.0 rad/(m·s);
  - forward speed clip(1.2 · along, 0.08, 0.3) m/s, and z clipped to ±0.3 while moving;
  - turn speed |z| clipped to [0.15, 0.5] rad/s;
  - acceleration limits (0.6, 0.6, 1.0).

  *Why:* the design asks for no sudden speed changes and at most 0.5 rad/s. *If wrong:* tune them in Task I.

Grid frame:
- The anchor pose (x0, y0, yaw0) is the centre of cell (0, 0), and heading 0 points along yaw0.
- The centre of cell (i, j) is (x0, y0) + R(yaw0)·(0.5 i, 0.5 j).
- Heading h ∈ {0, 1, 2, 3} is yaw0 + h·90°, counter-clockwise; `turn_left` adds 1.
- The grid's metric coordinates are local(x, y) = R(−yaw0)·((x, y) − (x0, y0)).

New `Session.snapshot()` keys:
```text
"objects":    [{"id","label","name","x","y","size":[sx,sy],"visible","seen","where"}]   ([] when none; "where" from the live pose, null without a pose)
"grid":       null | {"cell":0.5, "origin":[x0,y0], "yaw":yaw0, "i":[imin,imax], "j":[jmin,jmax],
                      "blocked":[[i,j],...], "robot":[i,j,h], "goal":[i,j,h]|null}
"plan_cells": [[i,j,h], ...]   destination of each step whose status != "done", aligned with those steps ([] without a grid)
```
Event names stay `world.event_name(action, label)`.

```python
CELL = STEP_DISTANCE                     # 0.5
MAX_CELLS = 256
BLOCK_MARGIN = 0.45
NEAR_MIN_MARGIN = 0.75; NEAR_MAX_MARGIN = 1.5; NEAR_MAX_DISTANCE = 1.4; NEAR_MAX_ANGLE_DEG = 40.0
RING_MIN_MARGIN = 0.75; RING_MAX_MARGIN = 1.75
SAFETY_PROPS = ("obstacle_front", "obstacle_back", "moved_forward", "moved_backward")
HEADINGS = ((1, 0), (0, 1), (-1, 0), (0, -1))     # h = 0..3 in the grid frame, counter-clockwise

@dataclass(frozen=True)
class GridState:
    cell: tuple[int, int]
    heading: int
    posture: str
    front: bool = False
    back: bool = False
    laps: tuple[int, ...] = ()             # progress 0..5 (LAP_DONE = 5) per GridWorld.lap_props

@dataclass(frozen=True)
class Snap:
    cell: tuple[int, int]; heading: int
    offset: float                          # [m] from that cell's centre
    yaw_error: float                       # [rad] absolute, from that heading's yaw

@dataclass(frozen=True)
class Grid:
    anchor: Pose                           # odom pose of the centre of cell (0, 0), heading 0
    i_range: tuple[int, int]               # inclusive
    j_range: tuple[int, int]

    def center(self, cell) -> tuple[float, float]: ...       # odom
    def heading_yaw(self, heading: int) -> float: ...        # odom, wrapped to (-pi, pi]
    def local(self, x: float, y: float) -> tuple[float, float]: ...
    def snap(self, pose: Pose) -> Snap: ...                  # nearest centre and nearest heading
    def to_json(self, robot: tuple[int, int, int] | None, goal: tuple[int, int, int] | None) -> dict: ...

class GridError(Exception): ...            # str(exc) is the user message

@dataclass
class GridWorld:
    world: World
    grid: Grid
    objects: tuple[Obj, ...]               # the Scene's objects, odom
    atoms: frozenset[str]

    near: dict[str, frozenset[tuple[tuple[int, int], int]]]  # near prop -> {(cell, heading)}
    def label(self, state: GridState, action: str | None) -> frozenset[str]: ...
    def step(self, state: GridState, action: str) -> tuple[str, GridState] | None: ...

    def observe(self, src: GridState, action: str, cell: tuple[int, int], heading: int) -> GridState | None: ...
```

Rules (the design §6.4 with R1, R3–R8 and R25):
- **Referenced objects** are the ids in `atoms` (via `split_prop`).
  - An id that is not in `objects` raises `GridError(msg_not_found(label))`.
  - Any referenced object whose centre is more than `MAX_OBJECT_DISTANCE` from the anchor raises `GridError(msg_too_far(label))`.
- **Rectangle:** work in the local frame, with each referenced object's outer band R (near: min(r + 1.5, 1.4); around and around_cw: r + 1.75; the largest one used).
  - On each axis, take [ceil((g − R)/CELL), floor((g + R)/CELL)].
  - Take the union of these over the objects, plus 0 (the robot's cell), and widen by 1 cell on each side.
  - An area over `MAX_CELLS` raises `GridError(MSG_TOO_SPREAD)`.
- **blocked:** the cells in the rectangle whose centre is within r + `BLOCK_MARGIN` of **any** object's centre, except (0, 0).
- **near:** (cell, h) for free cells with r + 0.75 ≤ d ≤ min(r + 1.5, 1.4) and |wrap(bearing to the centre − heading yaw)| ≤ 40°.
- **ring(obj):** free cells with r + 0.75 ≤ d ≤ r + 1.75.
- **sector:** atan2 from the object to the cell, in degrees within [−45, 315): [−45, 45) is 0, [45, 135) is 1, [135, 225) is 2, [225, 315) is 3.
- **`next_lap(p, a, b, cw)`**, where a and b are the sectors of the cells before and after a move (None for a cell that is not in the ring):
  ```text
  p == LAP_DONE (5) -> 5;  b is None -> 0;  a is None -> 0;  b == a -> p
  b == (a + 1) % 4 -> (p + 1 if not cw else 0);  b == (a - 1) % 4 -> (p + 1 if cw else 0);  else -> 0
  ```
  Turns, posture changes and gestures do not change `laps`.
- **`step(state, action)`:**
  - The destination posture comes from `ACTIONS[action].transitions` (None when there is none or it is unknown).
  - `forward` (and `backward`, only when `"moved_backward" in atoms`) moves to the next cell along `HEADINGS[h]`. It does not exist if that cell is blocked or outside.
  - `turn_left` adds 1 to the heading and `turn_right` subtracts 1 (mod 4).
  - Bits (R1): a destination that is not standing has (False, False); `stand` and `rise_sit` give (False, False); any other standing → standing action keeps the source bits.
- **`label(dst, action)`** (R25), as the union of:
  - {posture prop} ∩ atoms;
  - {action prop} if it is in atoms or in `SAFETY_PROPS`;
  - obstacle_front and obstacle_back when the bits are set;
  - near props when (cell, heading) is in `near[p]`;
  - lap props when their progress is `LAP_DONE` (5).
- **World:**
  - BFS from the initial state `GridState((0, 0), 0, posture, front and posture == STANDING, back and posture == STANDING, (0,) * len(lap_props))`, indexed with a dict.
  - Controllable transitions come from `step`.
  - Uncontrollable transitions in standing states toggle the bits as in `go2_sensor_events`; in other postures they are the 4 self-loops.
  - `marked` is all states; `initial_label = label(initial, None)`; `propositions = tuple(sorted(atoms | set(SAFETY_PROPS)))`; `forbidden` is the events whose label contains an unsafe set.
- **`observe(src, action, cell, heading)`:** the state `step` would give with its cell and heading replaced by the given ones, laps by `next_lap` from `src.cell` to `cell`. It is None when `step(src, action)` is None or when `cell` is blocked or outside.
- **Numerics** (so that a rotated or shifted anchor gives the same cells, and two builds never differ on a boundary):
  - All distance tests (blocked, near, ring) use `EPS = 1e-9` m: blocked is d ≤ r + 0.45 + EPS, and the bands are lo − EPS ≤ d ≤ hi + EPS.
  - The rectangle bounds use `ceil(round((g − R) / CELL, 9))` and `floor(round((g + R) / CELL, 9))`.
  - `sector` rounds the angle to 1e-6 degrees before it classifies, so the 4 diagonal ring cells of an object on the lattice (exactly 45°) always fall in the next sector counter-clockwise (N, W, S, E).
  - The near angle test is |wrap(bearing − heading yaw)| ≤ 40° + 1e-9 rad.
  - `Grid.snap` and `heading_yaw` wrap every yaw difference to (−π, π]. `DirectSimLink`'s yaw is never wrapped, and it passes 2π after one lap.

GridExecutor control law (P7, R11; `along` and `cross` are measured from the pose to `goal_xy`, along and across `goal_yaw`):
```text
turn:     err = wrap(goal_yaw - yaw); if |err| <= GRID_DONE_YAW -> settle
          z* = sign(err) * clip(1.5*|err|, 0.15, 0.5); x* = 0
forward:  along = d·u, cross = d·n  (d = goal - pos, u = (cos gy, sin gy), n = (-sin gy, cos gy))
backward: along = -d·u
          if along <= GRID_DONE_DIST -> settle
          x* = ±clip(1.2*along, 0.08, 0.3)   (+ forward, - backward)
          z* = clip(1.5*wrap(gy - yaw) ± 1.0*cross, -0.3, 0.3)   (+cross forward, -cross backward)
ramp vel toward (x*, 0, z*) with cfg.acc; send MOVE {"x","y":0,"z"} rounded to 3 decimals
settle:   on entry send [STOP] once, zero vel, settle_until = now + GRID_SETTLE_S;
          then send nothing until now >= settle_until, then _advance() (holds still apply)
timeout:  as Executor (ideal = value/speed, or radians(value)/cfg.speed[2]; margin 2.5, + 5 s) -> cancel
```
