## 結論

**controller の状態推定（Estimator）が、胴の座標の値と世界の座標の値を混ぜていたのが原因。2 つのパッチで直った。**

| パッチ（`docker/patches/`） | 直すこと | 大きさ |
|---|---|---|
| `0001-estimator-world-frame-leg-odometry.patch` | 脚の運動学の測定値（足の位置 `p_b`、速さ `J·q̇`）を、世界の座標（`R·p_b`、`R·(J·q̇ + ω×p_b)`）にしてからカルマンフィルタに入れる。振り出す足の速さ `getFeetVel()` も同じ。元の unitree_guide と同じ式 | 2 ファイル、+16 −3 行 |
| `0002-feet-end-calc-body-frame-stance-angle.patch` | 歩くに入るときに測る足の角度（`FeetEndCalc::init`）を、世界の座標から胴の座標に戻す（`Rᵀ` を掛ける） | 1 ファイル、+5 −1 行 |

- 0001 だけで、その場の旋回（左右とも）は合格する。ただし、**回った後にもう一度歩くに入る**（伏せて立つ、座って立ち上がる）と、最初の数歩でよろけて立てなかった。demo_script（左に 90° → 座る → 立ち上がる）がこれに当たるので、0002 も要る。
- `docker/Dockerfile.gazebo` が、固定した commit を `git checkout` して rosdep を入れた後、colcon でビルドする前に `docker/patches/*.patch` を名前の順に `git apply` する。upstream は書き換えていない。
- 物理の設定（xacro・world・launch）は変えていない。

### なぜ回ると転んだか

- Estimator のカルマンフィルタの状態（胴の位置・速さ、足の位置）は世界（IMU の基準）の座標。なのに port（ROS 2 版）は、脚の測定値を胴の座標のまま入れていた（`Estimator.cpp` 180〜181 行）。元の unitree_guide は `FrameType::GLOBAL` で回してから入れる。
- そのため、推定した胴の位置・速さは「向き ψ だけ回った」値になる。ψ = 0（起動したときの向き）では正しいので、まっすぐ歩くのは問題ない。
- 回った後は、StateTrotting の位置・速さの PD（`Kpp` 70・`Kdp` 10）と足の置き場所が ψ だけ回る。調べた結果の計算では |ψ| が約 59 度を越えると不安定になる。90 度回って止めた直後（0.1〜3 秒）に横へ倒れていたのはこれ。
- 0002 は同じ種類の誤り：`getFeetPos2Body()` は世界の座標なのに、`calcFootPos()` が今の向きをもう一度足す。歩くに入るのが ψ ≈ 0 のときだけなら表に出ない。

## 橋渡しの変更

### R22：歩くに入ってから 0.5 秒は Move の速度を入れない

- 窓口の 1013（BalanceStand の 0.5 秒後）は、体が本当に歩くに入るより先に出る。すぐ来た Move をそのまま入れると、controller は歩くに入った瞬間から速く歩き、よろける（Task 16 の Concern 2）。
- `BridgeCore` は、Move の速度を controller が歩くに入ってから `TROT_WAIT_S` = 0.5 秒（シミュレーションの時間）まで 0 のまま待たせ、それから入れる。待っている間も窓口は 1015。Move の 1 秒の期限（送り直しが無ければ止まる）は今までどおり実際の時間。待っている間に StopMove が来たら、速度は 1 通も出さない。
- 「歩くに入った」時刻：controller の伏せ・立つは、コードでは 1.8 秒（200 Hz × 1.2 × 1.5 回）だが、Gazebo で測ると 1.88〜1.92 秒（command を待っていたときは 2.0〜2.5 秒）だった。送った command からの見積もりは 0.1〜0.3 秒早くなる。
  そこで、橋渡しのノードは controller が `/rosout` に出す `Switched from fixed stand to trotting` を受けた時刻を `BridgeCore.trot_entered()` で知らせ、その 0.5 秒後から速度を入れる。知らせが来なければ、見積もりより 1.0 秒（`TROT_REPORT_LATE_S`）遅らせて入れ、ログに出す。
- 確かめ：demo A で、歩くに入ったのがシミュレーションの 8.66 秒、前進の速度を出したのが 9.18 秒（0.52 秒後）。
- テスト：`test_stand_then_walk_then_expire`（待ってから入る・1 秒の期限）、`test_move_waits_for_trot_entry_in_sim_time_and_stop_cancels_it`、`test_move_waits_for_reported_trot_entry`。

### R23：`/utlidar/cloud` から地面と体の点を除く

- 今までの「体の箱」（中心から前後 0.40 m・左右 0.20 m・高さ −0.35〜0.15 m、と当たらなかった本）に加え、**世界の z が 0.05 m 未満の点**を除く（`drop_ground_and_self_points`）。世界の z は Gazebo の本当の base の高さと向き（傾きも入れる）から出す。
- odometry がまだ来ていないうちは点群を出さない（地面を除けないため。起動して 1 秒もかからずに来る）。
- 確かめ（gazebo コンテナで、`/utlidar/cloud` を `voice_ltl.sensing.Sensing` に通した。比べるために、生の点から体の箱だけ除いた場合も通した）：

## 追記（Task 17）：止めた後に 1.0 秒待つのを試したが、入れなかった

Task 17 の確認（`gazebo_e2e.md` の 4）で、上の「歩いた後に回ると、大きく揺れることがある」を測り直した。式から直接・本物の Claude で動かし、動作ごとの最大 |roll| を Gazebo の本当の傾きで見た。

- 前進のすぐあとに回る（左 6 回・右 2 回）：最大 0.393 rad。0.5 は越えなかった。
- 0.5 を越えたのは、前進 → 前進（0.500・0.673）と、左 → 前進（0.543）。転んではいない。
- そこで ruling R33 の形（橋渡しだけ、`BridgeCore` で、歩いていたのを止めたら次の速度を 1.0 秒（シミュレーションの時間）0 のまま待たせる）を、テストを付けて入れ、7 回流した。前進 ×4 の 1 回で転び（裏返って起き上がった、roll 3.04）、もう 1 回で 1.12 rad になった。
